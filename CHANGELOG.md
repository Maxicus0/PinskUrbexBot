# Changelog

Начиная с этой версии релизы бота фиксируются здесь. Записи 0.1–0.3
восстановлены задним числом по истории git — подробностей по ним меньше,
чем будет у 0.4 и далее.

## Unreleased

**Бета-бот при каждом локальном запуске стирает свою SQLite и подтягивает
свежий снимок прода заново.** `BETA_BOT_TOKEN` (без `BOT_TOKEN`) — файл
`beta.db` рядом с проектом больше не хранится между запусками: каждый раз,
как стартует `python bot.py`, он полностью пересобирается из свежего
снимка `DATABASE_URL` (той же боевой PostgreSQL, что на Render, см.
`database/beta_sync.py`, `scripts/pull_from_production.py`). Персональные
данные копируются как есть, зашифрованными байтами, без расшифровки —
`APP_SECRET_KEY` для этого нужен ровно тот же, что и в бою (никакой
отдельной генерации ключа для беты больше нет — `utils/crypto.py` требует
`APP_SECRET_KEY` безусловно, в обоих режимах). Источник (боевая
PostgreSQL) открывается в транзакции `READ ONLY` и в конце всегда
откатывается — записать туда локальный запуск физически не может.
`scripts/reset_local_db.py` теперь просто удаляет `beta.db` без повторного
подтягивания (пересборка при следующем `python bot.py` и так сделает то же
самое).

Боевой режим (`BOT_TOKEN` + `DATABASE_URL`, PostgreSQL) не изменился.

## 0.4 — 2026-08-31

**Инсайды больше не копятся в БД.** Раньше оценённый инсайд (текст, медиа,
статус, кредиты) навсегда оставался в таблице `insights`. Теперь это только
очередь на модерацию: строка живёт в БД, пока не обработана, и удаляется
сразу же, как только админ доводит её до конца — оценкой (при отказе на 0 —
обязательно с причиной) и, при желании, заметкой об авторе. Начисленные
кредиты доверия при этом не теряются — они уже записаны в `users.credits`
до удаления. Содержимое инсайда после обработки остаётся только в переписке
админа с ботом в Telegram, БД его больше не хранит. Это защищает от
разрастания базы (актуально для бесплатных тарифов PostgreSQL с лимитом
объёма) и снижает объём личных данных, которые вообще хранятся на сервере.
**Обновление со старых версий подчищает и уже накопленный мусор:** при
первом запуске на 0.4 любые строки `insights`, оставшиеся от старого
поведения (`status` не `pending` — то, что раньше годами копилось как
`approved`/`rejected`), удаляются одной миграцией
(`database.init_db._purge_legacy_rated_insights`); повторные запуски
безопасны, no-op.

- `database.insights_repo.set_insight_rated()` (UPDATE, хранил запись
  навсегда) заменён на `delete_insight()` (DELETE, каскадно удаляет
  `insight_media`).
- **0 кредитов за инсайд теперь требует текстовую причину отказа.** Раньше
  админ мог отклонить инсайд одним числом без объяснений — автор просто
  получал «Ваш инсайд отклонён модератором» и всё. Теперь отказ на 0
  переводит админа в отдельный обязательный шаг: без текста причины оценку
  завершить нельзя («-» тоже не подходит, в отличие от последующей
  необязательной заметки об авторе). Причина уходит автору вместе с
  уведомлением об отказе — личность автора ему по-прежнему не раскрывается.
- **Очередь инсайдов больше не требует лишнего клика.** Кнопки «✅ Оценить
  инсайд» и «⏭ Пропустить без оценки» под карточкой инсайда убраны — кнопка
  «📋 Ожидающие инсайды» сразу показывает карточку и следом же запрашивает
  число кредитов доверия («Введите число кредитов доверия (0–10) за инсайд
  #X. 0 = отклонить инсайд.»), без промежуточного выбора действия. Под этим
  запросом — одна кнопка «🔙 Назад в меню» для админа: прерывает оценку без
  изменений, инсайд остаётся pending и просто ждёт своей очереди дальше.
- **Превью перед отправкой инсайда показывает настоящие медиа.** В «👀
  Проверьте перед отправкой» вместо строки-счётчика «Медиа: 2 фото + 1
  видео» теперь показываются сами прикреплённые фото/видео — тем же
  способом, каким их увидит админ при оценке.
- **Формат карточек объектов в списке архива:** `🗂 Название 📍` — только
  общая иконка архива и название (плюс 📍, если у объекта есть координаты),
  без эмодзи уровня опасности на самой кнопке. Уровень опасности
  (⚪🟢🟡🔴⚫) остаётся виден внутри карточки объекта — на кнопке списка он
  больше не палится заранее.
- **Новая команда `/about`.** Отвечает ссылкой на GitHub-репозиторий
  проекта из переменной окружения `GITHUB_REPO_URL` (см. `.env.example`,
  `render.yaml`) — просто и честно показывает, что исходники открыты.
  Переменная необязательная: если её не заполнить, бот не падает и не
  ломает запуск — `/about` в этом случае просто отвечает, что автор,
  похоже, обнаглел и закрыл исходники, и создатель бы такое точно не
  одобрил (см. `handlers/common.py`, `cmd_about`).
- **README: раздел «Безопасность и анонимность» поднят в начало файла**
  (сразу после описания проекта, перед «Быстрый старт») — это самое важное,
  что должен узнать о боте новый читатель, не долистывая до середины
  документа. Туда же добавлен пункт про прозрачность/`/about`.
- Полная отладочная проверка кодовой базы:
  - Убрано мёртвое поле `bonus_word` из каждого праздника в
    `utils/holidays.py` — оно нигде не читалось (реальное склонение всегда
    вычисляла `_bonus_word()` через `plural_credits()`) и могло незаметно
    разойтись с `bonus_credits` при правке.
  - Убрана мёртвая функция `danger_emoji()` из `utils/danger_levels.py` —
    осталась неиспользуемой после того, как эмодзи уровня опасности убрали
    с тизера объекта в списке архива (см. пункт про формат карточек выше).
  - Закрыты «немые» тупики в сценарии отправки инсайда и его оценки: если
    пользователь или админ присылал неожиданный тип сообщения (голосовое,
    стикер, GIF и т.п.) в разгар диалога, бот раньше просто ничего не
    отвечал — теперь во всех соответствующих состояниях FSM есть понятная
    подсказка, что делать дальше.
  - Та же категория бага закрыта и в сценариях **добавления и
    редактирования объекта архива** (`handlers/admin_add_object.py`,
    `handlers/admin_manage_objects.py`) — раньше про них забыли: девять
    состояний FSM (название, фото объекта, фото залаза, история, состояние,
    слухи, координаты, порог доступа, выбор уровня опасности, подтверждение
    сохранения — плюс `EditObjectForm.waiting_value`/`waiting_photos` при
    редактировании) молчали в ответ на неподходящий тип сообщения. Теперь
    везде есть явная подсказка.
  - Исправлена испорченная опечаткой формулировка в приглашении оставить
    заметку об авторе инсайда (`handlers/admin_rate_insight.py`,
    `_prompt_for_note`).
  - Почищены докстринги, ссылавшиеся на уже удалённую кнопку «⏭ Пропустить
    без оценки» (`database/insights_repo.py`) и на переименованную функцию
    входа в оценку (`keyboards/insight_kb.py`, `rating_back_kb` — ссылка
    поправлена на актуальную `present_insight_for_rating`).

**telegram_id и другие персональные данные в БД теперь зашифрованы, а не
лежат открытым текстом.** Тот, у кого есть только дамп базы (бэкап,
скомпрометированный доступ, утечка у хостинг-провайдера), не может по нему
восстановить ни один telegram_id или имя — для этого нужен ещё и
`APP_SECRET_KEY`, который в БД никогда не попадает.

- Зашифрованы (см. новый модуль `utils/crypto.py`): `users.telegram_id`
  (PK), `users.username`, `users.full_name`, `objects.created_by`,
  `insights.user_id`, `user_notes.user_id`, `user_notes.admin_id`,
  `user_notes.text`. Не тронуто намеренно — тексты инсайдов/объектов,
  credits, даты: рабочий контент бота, не персональные данные конкретного
  человека, шифровать их не было смысла.
- Два алгоритма под две разные задачи: AES-256-SIV (RFC 5297,
  детерминированное AEAD) для telegram_id и всего, что на него
  ссылается, — единственный способ сохранить `WHERE`/`JOIN` по
  зашифрованной колонке рабочими без расшифровки всей таблицы на каждый
  запрос; AES-256-GCM (случайный nonce) для username/full_name/текста
  заметок, где точечный поиск по значению не нужен и важнее не давать вовсе
  никакой информации о содержимом.
- **Ключ шифрования настраивается одной переменной — `APP_SECRET_KEY`** (см.
  `.env.example`) — и не придумывается человеком: генерируется как настоящая
  случайность (`scripts/generate_secret_key.py`, новый скрипт); на Render
  его генерирует сама платформа (`render.yaml`, `generateValue: true`) —
  ключ никогда не проходит через дашборд как редактируемый текст. Сам секрет
  никогда не используется как ключ шифрования напрямую — проходит
  HKDF-SHA256 с разными info-метками на каждую цель (AES-GCM- и AES-SIV-ключ
  криптографически независимы, хоть и выведены из одного секрета). Бот
  отказывается стартовать, если ключ пуст или короче 256 бит. Шифротекст
  версионирован (1 байт префикса) — задел на будущую ротацию ключа без
  даунтайма и без разовой перешифровки всей базы.
- **Обновление со старых версий (где эти колонки ещё `BIGINT`/`TEXT`)
  происходит само, без ручных действий администратора:** при первом запуске
  на 0.4 `database.init_db._migrate_v04_encrypt_pii` шифрует накопленные
  данные на месте и меняет типы колонок — идемпотентно (прогресс
  определяется по фактическому типу `users.telegram_id` в БД, а не
  отдельным флагом), одной транзакцией (сбой на середине откатывает всё
  целиком, база остаётся в прежнем рабочем состоянии для повторной попытки
  на следующий старт), без стороннего инструментария — то же соединение,
  что делает `CREATE TABLE IF NOT EXISTS` из `schema.sql`.
- **`/about` — добавлен блок FAQ.** Под основным текстом команды теперь
  есть кнопка «Почему этот бот анонимен?» — по нажатию бот присылает
  развёрнутый ответ, пересказывающий своими словами раздел README
  «Безопасность и анонимность» (см. `handlers/common.py`,
  `keyboards/common_kb.py`).
- **Новая команда `/settings`.** Личный переключатель отображения объектов
  в списке «🗂 Архив»: стандартный вид (общая иконка 🗂, как раньше, выбран
  по умолчанию) или с эмодзи фактического уровня опасности объекта вместо
  иконки. Выбор сохраняется на пользователя (новая колонка
  `users.archive_display_mode`) и не виден другим — см.
  `handlers/settings.py`, `keyboards/settings_kb.py`,
  `utils.formatting.format_object_teaser`.
- **`scripts/smoke_test.py` больше не требует ни `APP_SECRET_KEY`, ни
  отдельной тестовой БД.** Если ключа нет в окружении, тест генерирует
  разовый случайный на время своего запуска — реальным зашифрованным
  данным он не нужен, поскольку весь сценарий выполняется в одной
  транзакции БД (`database.db.test_transaction`), которая в конце ВСЕГДА
  откатывается, что бы внутри ни случилось. Поэтому `DATABASE_URL` можно
  без риска указывать ту же базу, на которой уже работает боевой и/или
  бета-бот (см. README, «Бета-бот для локального теста»): пока тест
  выполняется, они его правок не видят (обычная изоляция транзакций
  PostgreSQL), а после отката от них не остаётся следа. Дополнительная
  страховка на случай, если эту транзакционность в будущем случайно
  сломают рефакторингом, — тестовые `USER_ID`/`ADMIN_ID` намеренно взяты
  далеко за пределами диапазона настоящих `telegram_id`.
