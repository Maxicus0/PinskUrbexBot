# PinskUrbexBot

Telegram-бот — архив заброшенных объектов города, работающий на
**кредитах доверия**: пользователи присылают инсайды (новый объект,
залаз, координаты, новости, до 5 фото/видео), админы оценивают их числом,
за это начисляются кредиты, которые открывают доступ к карточкам объектов.
У каждого объекта архива есть обязательный уровень опасности
(⚪🟢🟡🔴⚫, см. `config.DANGER_LEVELS`), который назначает админ.

Стек: Python, aiogram 3, PostgreSQL (боевой бот) / SQLite (локальный
бета-бот, см. «Бета-бот для локального теста» ниже).

## Безопасность и анонимность

- **Бот не скачивает и не хранит у себя присланные файлы.** И для инсайдов
  (`insight_media`), и для фото объектов (`object_photos`) в базе хранится
  только Telegram `file_id` — ссылка на файл, который остаётся на серверах
  Telegram. Сам бот байты файла нигде не сохраняет и никуда не пересылает.
- **К инсайду принимаются только фото/видео, отправленные как обычное медиа**
  (не как файл/документ). Именно в таком виде Telegram сам сжимает и
  переупаковывает вложение при загрузке — вместе с этим стираются служебные
  метаданные, в т.ч. GPS-координаты съёмки и модель устройства. Документы
  Telegram передаёт как есть, без этой обработки, поэтому такие вложения
  бот отклоняет явным сообщением с объяснением (см.
  `handlers/insight_submit.py`).
- **Уведомления об инсайдах анонимны.** При поступлении инсайда админ сразу
  видит только счётчик очереди («Всего в очереди: N») — без текста и медиа.
  Содержимое (текст, фото/видео, порядковый номер) и сразу следующий за ним
  запрос оценки показываются только когда админ сам открывает очередь
  («📋 Ожидающие инсайды»), и никогда — имя, username или telegram_id
  автора (см. `utils.formatting.format_insight_notification`). Оценка не
  может быть предвзятой к конкретному человеку.
- **Инсайды оцениваются по одному, а не списком.** Кнопка «📋 Ожидающие
  инсайды» сразу ведёт к оценке самого старого инсайда в очереди — карточка
  инсайда и следом сразу запрос числа кредитов, без промежуточных кнопок
  выбора. После оценки бот автоматически показывает следующий по порядку
  поступления, и так далее, пока очередь не закончится (см.
  `handlers/admin_rate_insight.py`, `present_insight_for_rating` и
  `_advance_to_next_insight`).
- **Номера инсайдов не выдают историю.** Показывается позиция в очереди
  ожидающих, отсчитанная от нового к старому (самый новый = #1, самый
  старый = #N, где N — текущая длина очереди), а не сквозной id из БД —
  иначе номер сам по себе говорил бы, сколько всего инсайдов когда-либо
  прислали (см. `database.insights_repo.get_queue_position`).
- **Инсайды в БД хранятся только временно, транзитом, а не постоянным
  архивом.** Строка в таблице `insights` живёт ровно до того момента, как
  админ довёл его обработку до конца — оценил (при отказе на 0 кредитов —
  обязательно с причиной, см. ниже) и, при желании, оставил приватную
  заметку об авторе. Сразу после этого запись и все её медиафайлы
  (`insight_media`) удаляются из БД навсегда (см.
  `database.insights_repo.delete_insight`) — это не
  даёт базе бесконечно расти от текстов и медиа каждого когда-либо
  присланного инсайда (актуально для бесплатных тарифов PostgreSQL с
  лимитом объёма, см. раздел «Деплой на Render» ниже). Начисленные кредиты
  доверия при этом никуда не пропадают — они уже переведены в `users.credits`
  до удаления. Содержимое конкретного инсайда после обработки можно найти
  только в переписке админа с ботом в Telegram (карточка, которую бот
  прислал при открытии очереди, никуда не удаляется) — в самой БД его
  больше нет. На базах, заведённых ещё до 0.4 (где раньше такие строки
  оставались навсегда), это правило распространяется и на уже
  накопившуюся историю — см. следующий пункт.
- **0 кредитов за инсайд — это отказ не молча.** Если админ оценивает
  инсайд в 0, бот обязательно попросит его тут же одним сообщением указать
  текстовую причину — без неё оценку завершить нельзя. Причина уходит
  автору инсайда вместе с уведомлением об отказе, чтобы человек понимал, что
  не так, при этом личность автора ему по-прежнему не раскрывается (см.
  `handlers/admin_rate_insight.py`, `apply_reject_reason`).
- **Обновление с версий до 0.4 не оставляет старый мусор.** До 0.4 каждый
  уже оценённый инсайд навсегда оставался в `insights` — таблица работала
  как постоянный архив. При первом запуске на 0.4 вся такая история
  (всё, что не в статусе `pending`) удаляется одной миграцией
  (`database.init_db._purge_legacy_rated_insights`) — повторные запуски
  безопасны, на уже мигрированной базе это no-op.
- **telegram_id и другие персональные данные в БД зашифрованы, а не лежат
  открытым текстом.** `users.telegram_id` (и все колонки, которые на него
  ссылаются — `objects.created_by`, `insights.user_id`,
  `user_notes.user_id`/`admin_id`), а также `username`, `full_name` и текст
  приватных заметок админа — хранятся в PostgreSQL как непрозрачные `bytea`
  (см. `database/schema.sql`, `utils/crypto.py`). Тот, у кого есть только
  дамп базы (бэкап, скомпрометированный доступ к БД, утечка у хостинг-
  провайдера), не может по нему восстановить ни один telegram_id или имя —
  для этого нужен ещё и `APP_SECRET_KEY`, который в БД никогда не попадает
  (см. раздел «Ключ шифрования» ниже). Как и с историей инсайдов выше, базы,
  заведённые до 0.4 (там эти колонки ещё обычные `BIGINT`/`TEXT`),
  мигрируются на зашифрованную схему автоматически при первом запуске на
  0.4 (`database.init_db._migrate_v04_encrypt_pii`) — вручную ничего
  делать не нужно, повторные запуски на уже мигрированной базе — no-op.
- **Прозрачность: исходный код открыт.** Команда `/about` показывает ссылку
  на GitHub-репозиторий проекта из `GITHUB_REPO_URL` (см. `.env.example`,
  `render.yaml`). Переменная необязательная — если её не заполнить, бот всё
  равно нормально запустится, а `/about` просто честно ответит, что автор,
  похоже, обнаглел и закрыл исходники (см. `handlers/common.py`, `cmd_about`).
- **`/about` объясняет анонимность по кнопке.** Под текстом команды есть
  блок «FAQ:» с кнопкой «Почему этот бот анонимен?» — по нажатию бот
  присылает развёрнутый ответ, который своими словами пересказывает все
  пункты этого раздела README (см. `handlers/common.py`, `_faq_anon_text`).

### Ключ шифрования

`APP_SECRET_KEY` — единственный секрет, без которого зашифрованные
telegram_id/username/full_name/заметки в БД невозможно прочитать (см.
`utils/crypto.py`). Несколько вещей, которые отличают его от «случайной
строки в .env»:

- **Ключ никогда не придумывается вручную.** Сгенерируйте настоящую
  случайность: `python -m scripts.generate_secret_key`. При старте бот сам
  откажется запускаться, если `APP_SECRET_KEY` пустой или короче 256 бит —
  это защита именно от «банальных» ключей (человек обычно придумывает
  что-то предсказуемое и переиспользуемое, а не 256 честных случайных бит).
- **На Render ключ не проходит через ваши руки вообще.** `render.yaml`
  использует `generateValue: true` — платформа сама генерирует случайный
  ключ при первом деплое, не показывая его как редактируемый текст в
  дашборде. Значение стабильно между деплоями одного и того же сервиса, так
  что уже накопленные зашифрованные данные не «протухнут» при обычном
  редеплое.
- **Оба алгоритма реализованы через `cryptography` (не самописная крипто-
  математика):** AES-256-GCM для полей, по которым в SQL не бывает
  точечного поиска (username, full_name, текст заметки) — со случайным
  nonce на каждое значение, и AES-256-SIV (RFC 5297) для telegram_id и всех
  колонок, которые на него ссылаются, — детерминированное шифрование,
  единственный способ сохранить `WHERE`/`JOIN` по зашифрованной колонке
  рабочими без расшифровки всей таблицы на каждый запрос. Подробности и
  разбор компромиссов — в docstring `utils/crypto.py`.
- **Если ключ потерян или заменён на другой** — все зашифрованные данные в
  БД навсегда нечитаемы (расшифровка при неверном ключе завершается
  ошибкой `InvalidTag`, а не тихо возвращает мусор), а поиск пользователя по
  telegram_id просто ничего не находит (запись выглядит так, будто её нет).
  Резервная копия ключа обязательна, если данные в БД для вас ценны —
  храните её отдельно от `.env` и от самой БД (менеджер паролей и т.п.).
  Формат шифротекста включает версию ключа (см. `utils/crypto.py`,
  `_KEY_VERSIONS`), так что при необходимости ротации можно добавить новую
  версию, не трогая уже накопленные записи старой.

`APP_SECRET_KEY` обязателен и одинаков в обоих режимах — см. «Бета-бот
для локального теста» ниже про то, зачем он нужен и локальному запуску.

## Быстрый старт

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# впишите в .env: BOT_TOKEN (от @BotFather), ADMIN_IDS (ваш telegram id),
# DATABASE_URL (строка подключения к PostgreSQL)
# GITHUB_REPO_URL — необязательно, ссылка на этот репозиторий для команды /about

# сгенерируйте ключ шифрования персональных данных (см. «Ключ шифрования» выше)
# и впишите его в .env как APP_SECRET_KEY:
python -m scripts.generate_secret_key

python bot.py
```

Схема БД создаётся автоматически при первом запуске (`database/schema.sql`).
При обновлении с версий до 0.4 при первом же старте автоматически
подчищаются оценённые/отклонённые инсайды, накопленные в базе ещё до
перехода на временное хранение очереди, а telegram_id и другие персональные
данные шифруются на месте (см. раздел «Безопасность и анонимность» выше и
`database/init_db.py`, `_purge_legacy_rated_insights`,
`_migrate_v04_encrypt_pii`).

## Настройки отображения архива

Команда `/settings` — личная настройка пользователя, не влияет ни на кого,
кроме него самого. Пока в ней один переключатель: как подписаны кнопки
объектов в списке «🗂 Архив» (см. `config.ARCHIVE_DISPLAY_MODES`,
`utils.formatting.format_object_teaser`):

- **Стандартный** (выбран по умолчанию) — у каждого открытого объекта общая
  иконка 🗂, без намёка на уровень опасности, чтобы риск не палился заранее
  прямо на кнопке (он виден только внутри самой карточки объекта).
- **С цветом опасности** — вместо 🗂 подставляется эмодзи фактического
  уровня опасности объекта (⚪🟢🟡🔴⚫, см. `config.DANGER_LEVELS`), название
  и 📍 (если есть координаты) остаются на месте.

Скрытые по кредитам доверия объекты всегда показываются как
«🔒 Порог доступа: N кредитов доверия», независимо от выбранного режима, —
переключатель влияет только на уже открытые пользователю объекты. Выбор
сохраняется в `users.archive_display_mode` (см. `database/users_repo.py`) и
применяется при каждом следующем открытии «🗂 Архив».

### Бета-бот для локального теста

`BETA_BOT_TOKEN` — токен **второго** бота (от @BotFather) для локальных
запусков (например, из PyCharm). Активен всегда только один бот:

- `BOT_TOKEN` заполнен → боевой режим — бот работает напрямую с
  PostgreSQL (`DATABASE_URL`);
- `BOT_TOKEN` пуст, заполнен `BETA_BOT_TOKEN` → бета-режим — **при каждом
  запуске** (`python bot.py`) локальный файл **SQLite** (`beta.db`,
  создаётся сам рядом с проектом) полностью стирается и пересобирается
  заново из свежего снимка той же `DATABASE_URL` (см.
  `database/beta_sync.py`). Дальше бета-бот работает только со своей
  локальной копией и в саму `DATABASE_URL` больше не пишет ни строки — так
  что как угодно ломать локальные данные во время теста можно спокойно, на
  следующем запуске всё равно всё стирается и подтягивается заново.

`DATABASE_URL` и `APP_SECRET_KEY` для этого нужны **те же**, что и у
боевого бота (можно взять прямо из дашборда Render → Environment) —
персональные данные копируются как есть, зашифрованными байтами, без
расшифровки: раз ключ тот же самый, шифротекст остаётся рабочим и в
локальной SQLite. Другим ключом (или без ключа) прочитать подтянутые
данные не выйдет — расшифровка просто упадёт с ошибкой.

```bash
python -m scripts.pull_from_production   # то же самое вручную, без перезапуска бота
python -m scripts.reset_local_db         # просто стереть beta.db, не подтягивая заново
```

⚠️ `file_id` фотографии привязан к боту, который её принял, — через другой
бот её не переслать (Telegram ответит `Wrong file identifier`). У объектов,
подтянутых с прода, карточка откроется без фото — это ожидаемо и не
ошибка, просто Telegram не отдаёт чужой файл по чужому токену.

Нужно погонять именно **боевого** бота локально (не бета, чтобы, например,
проверить сам polling, а не только слой БД)? Впишите `BOT_TOKEN` вместо
`BETA_BOT_TOKEN` — `DATABASE_URL`/`APP_SECRET_KEY` уже настроены на то же
самое. Учтите: пока запущены два процесса с одним `BOT_TOKEN` (этот и тот,
что уже крутится на Render), они будут конфликтовать за long polling — на
время локальной проверки либо останавливайте сервис на Render, либо не
указывайте `BOT_TOKEN` локально (оставайтесь на `BETA_BOT_TOKEN`).

Проверить слой БД и утилиты без Telegram (только PostgreSQL):
```bash
python -m scripts.smoke_test
```
`APP_SECRET_KEY` для этого можно не указывать — тест сгенерирует разовый
случайный сам. `DATABASE_URL` можно смело указывать ту же базу, что у
боевого бота: весь сценарий выполняется в одной транзакции, которая в
конце всегда откатывается, так что тест ничего в базе не меняет (см.
`database/db.py`, `test_transaction`).

## Структура

```
bot.py                 Точка входа
config.py              Конфигурация из .env
database/              Подключение к БД (PostgreSQL/SQLite), схема, репозитории
handlers/               Обработчики сообщений и колбэков
keyboards/              Клавиатуры
states/                 FSM-состояния
utils/                  Форматирование, доступ, уровни, валидация координат,
                        доставка сообщений при двух ботах (bot_delivery.py),
                        шифрование персональных данных (crypto.py)
scripts/smoke_test.py            Самопроверка БД без Telegram (PostgreSQL)
scripts/generate_secret_key.py   Генератор APP_SECRET_KEY
scripts/pull_from_production.py  Ручной перезапуск подтягивания снимка прода в beta.db
scripts/reset_local_db.py        Просто стереть beta.db, без повторного подтягивания
```

Вся работа с БД — только через `database/*_repo.py`. Любой пользовательский
текст в сообщениях бота проходит через `utils.formatting.esc()` (бот
работает с `ParseMode.HTML`) — кроме истории/состояния/слухов объекта, где
вместо esc() используется `utils.formatting.rich_text_or_none()`, сохраняющий
форматирование Telegram (жирный, курсив, зачёркнутый, код и т.п.), которое
админ применил при вводе текста.

## Деплой на Render

Конфигурация — в `render.yaml` (Blueprint): Web Service + managed
PostgreSQL, оба на бесплатном тарифе. Бот работает через long polling, а
не через HTTP, но у Render бесплатный план есть только у Web Service —
поэтому `bot.py` дополнительно поднимает лёгкую HTTP-заглушку на `$PORT`
(`GET /health` → `200 OK`) только для healthcheck'а самого Render.

### Пуш на GitHub

```bash
git init -b main            # если репозиторий ещё не инициализирован
git add .
git commit -m "Release 0.1"
git remote add origin git@github.com:<ваш-аккаунт>/PinskUrbexBot.git
git push -u origin main
```

`.env` в коммит не попадёт — он в `.gitignore`.

### Деплой

1. В [Render Dashboard](https://dashboard.render.com) → **New** → **Blueprint** → выберите репозиторий на GitHub.
2. Render прочитает `render.yaml`, попросит `BOT_TOKEN` (от @BotFather) и `ADMIN_IDS` — впишите вручную, в репозитории их нет.
3. `DATABASE_URL` подставится сама из связанной free-базы.
4. `APP_SECRET_KEY` (ключ шифрования персональных данных, см. «Ключ
   шифрования» выше) Render сгенерирует сам — вводить его не нужно, в
   диалоге создания Blueprint он не появится.

Оговорки бесплатного тарифа:
- **Web Service засыпает** после ~15 минут без HTTP-запросов и просыпается ~30-60 сек по следующему. Сам бот HTTP-трафик не получает, поэтому для действительно круглосуточной работы нужен внешний пингер — например, бесплатный [UptimeRobot](https://uptimerobot.com), раз в 10 минут дергающий `https://<ваш-сервис>.onrender.com/health`.
- **Free PostgreSQL живёт 30 дней**, потом Render её удаляет. Для боевой эксплуатации нужно поменять `plan: free` на `basic-256mb` (или выше) у базы в `render.yaml`.

## FAQ

**Зачем боевому и бета-боту разные СУБД (PostgreSQL/SQLite), а не одна?**
Это самый простой способ гарантировать, что локальный тест не может
*записать* что-то в продакшн: бета-бот только читает `DATABASE_URL` (в
транзакции `READ ONLY`, которая всегда откатывается) и дальше работает
исключительно с локальным файлом `beta.db` — писать в боевую базу ему
физически нечем.

**Локальный бета-бот не запускается / жалуется на БД — что делать?**
Он всё равно пересобирает `beta.db` с нуля при каждом запуске, так что
почти любая проблема лечится просто повторным `python bot.py`. Если нет —
`python -m scripts.reset_local_db` стирает файл, чтобы начать совсем
начисто.

**Почему бета-бот вообще требует `DATABASE_URL`, если работает на SQLite?**
`DATABASE_URL` тут — не рабочая база бета-бота, а источник, из которого
при каждом запуске подтягивается свежий снимок в `beta.db` (см.
`database/beta_sync.py`). Без него неоткуда брать данные для теста.

**Можно ли потестировать именно боевого бота локально (не бета)?**
Да — впишите `BOT_TOKEN` вместо `BETA_BOT_TOKEN`, `DATABASE_URL`/
`APP_SECRET_KEY` уже настроены на то же самое. Не запускайте его
одновременно с тем, что уже крутится на Render (см. «Бета-бот для
локального теста»).

**Почему `APP_SECRET_KEY` для бета-бота должен быть тем же, что и на Render?**
Подтянутые из прода данные копируются как есть, зашифрованными байтами —
локальный бета-бот их не расшифровывает и не шифрует заново. Расшифровать
их сможет только тот ключ, которым их зашифровал боевой бот; другим (или
без ключа вовсе) чтение упадёт с ошибкой.
